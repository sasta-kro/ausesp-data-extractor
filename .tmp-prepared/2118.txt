ABSTRACT 
Checklists are everywhere, they help us to reduce failure by compensating for 
potential limits of human memory and attention. Especially when it comes to facility 
management, checklists are a good tool for the people who feed the system with data 
such that  every time there is a routine to be followed, the person can just use a 
checklist to not forget anything. Similar to when we go grocery shopping and do not 
prepare a list , often we buy unnecessary things, and worse we forgot things that we 
urgently need.  This is the reason EBCsoft GmbH is developing Vormula Editor, 
Vormula App and VitriApp -Aufträge. With the Vormula Editor, the customer can 
create custom checklists with endless possibilities. To use these checklists, the 
customer has two cho ices: Vormula App, a simple mobile application where the user 
can download checklists from the Vormula Editor, fill them out, and export them via 
email. Second, the VitriApp-Aufträge, which also has all the features of the Vormula -
App but can connect with the Vitricon CAFM. Both of these applications are already 
in production and available for Android, iOS, and UWP. After an initial proof of 
concept prototype at the beginning of 2020, I began working on developing both 
applications in April 2021. Even thoug h both applications are already in use by our 
customers, the applications are still in active development , as customers require more 
and more features. Because of this, it was and still is very important to keep the code 
quality at high standards such that  new features and changes can be implemented 
quickly. This is reached by using design patterns and principles like Clean Code, 
Clean Architecture, and SOLID principles.

1.3 Overall Description 
The order app is a mobile application with which orders can be processed that have 
been created in  the CAFM syste m.  In the CAFM system, all topics related to the 
maintenance, care and modernization of buildings are managed. This includes a 
number of services that need to be performed. In the projects and orders area, these 
services are managed. It is possible to cre ate regular interval appointments or 
individual appointments for a wide variety of inspections and work. Based on order 
categories (e.g.: maintenance orders) or order objects (e.g.: air conditioning), 
individually configurable checklists can be assigned. A  checklist corresponds to a 
form that must be filled out by the user in the app lication. The checklist is linked to 
the order in the CAFM system and then the order and associated appointments, 
including the checklist, are transferred to the order app lication. In the application, the 
checklists and the associated appointment details are then filled digitally and sent 
back to the CAFM system after processing. 
1.3.1 User Needs 
The users of the order app are usually service providers who carry out certain 
activities within the buildings. Using the app, they are shown the jobs assigned to 
them. When an appointment takes place on site in the building, they can log it 
digitally in the app. First, define the start and end time, enter remarks, then sign 
everything digitally, and second, fill out the attached checklist. Once the appointment 
has been successfully completed, the service provider can send their entries back to 
the CAFM system. If the service provider receives an order without a specific 
appointment, he can also  create a new appointment in the AUAPP in order to be able 
to organize his work planning more flexibly. 
Use Case: Janitor’s duties 
A janitor has to go to a house once per week and perform different tasks. 
First, an appointment sequence is created in the CAFM system and assigned to the 
janitor. He gets an order with the category "Maintenance". A checklist "regular janitor 
activities" is created to this order category.  
Content of the checklist: 
1. Empty garbage cans 
2. Mow the lawn 
3. Clean stairs 
4. What is the condition of the house? 
5. Are there any actions that need to be taken? 
Now when the janitor goes to the house every Monday 8am, he opens his AUAPP, the 
job, the appointment and enters the start time. Then he opens the checklist and fills it. 
After that he enters the end time, fills in the comment, if necessary, changes the status 
of the appointment to complete it and lastly give his signature. The janitor then clicks

Use case 2: Air conditioning company 
An air conditioning company is contracted to maintain the air conditioning system in 
a building once a year. 
An order is created in the CAFM system with the category "Maintenance". The

object (technic al system).  There is no appointment, only the order with the order 
object and the assignment to the air conditioning company. 
The company gets the order displayed in the app and can create the appointment there 
independently. The scheduling of the exact ti me is done by the company itself.  When 
the appointment is due, it is opened, the start time is entered and the user navigates to

system" is opened and filled with details on the spot.

order items in one order, scanning the inventory QR code will uniquely identify the 
correct item. Only one result per checklist and order item may be generated.  Then the 
appointment is closed in the usual way and sent back to the CAFM system.

1.4.4 Non-functional Requirements 
Performance 
1. The applications must handle checklists with up to 250 controls without 
problems. 
2. For each list page (checklist, order, appointment, order item) the application 
should handle a count of 10,000 each with opening corresponding pages in 
less than 3 seconds. 
Security 
1. A new security token must be generated from the user details when 
communication with external APIs to make sure of the timeliness of the user’s 
credentials. 
2. All data must be encrypted before persisting on the device. 
3. All communication needs to use SSL when communication with external 
APIs.  
Quality 
1. The application should not unexpectedly crash 
2. If the synchronization fails, the data on the device should be kept to 
synchronize at a later point in time 
3. If something does not work as expected, a dialog should appear that informs 
the user that something went wrong, in the best case it should tell the us er 
what went wrong 
4. A log must be kept to find and solve bugs more efficiently

2.2.2 Layers 
Data Source and Data Access 
The first two layers of the mobile application are the data source and data access 
layer. The application is using entity framework core 3.1 (EF) to handle the 
responsibility for both layers. The Entity Framework is a set of technologies that 
support the development of data-oriented software applications. Developers can work 
with data in the form of domain -specific objects and properties, such as order and 

--- page 23 ---
17 
 
order items, without having to concern themselves with the underlying database tables 
and columns where this data is stored. 
 
Figure 2.4. Entity Framework [2] 
The above diagram shows how Entity Framework works under the hood. It takes our 
conceptional model (domain model) and maps  it to a storage model. This storage 
model is then saved in an SQLite database on the device itself. EF is using SQL for all 
interactions with the local database therefore the performance is almost as good as 
using SQL statements directly. 
Domain Model Layer 
The domain model layer defines the conceptual models of the application. The 
domain model contains all of the system’s object representations of data in the 
system. This also includes associated methods for any objects that contain their own 
functionality. 
Business Logic Layer 
The business logic layer  of the application is to encapsulate the applications 
controllers and services which implement much of the core business logic. It will also 
serve as the connection between the user interface and t he domain model, thus 
maintaining the separation of concerns. 

--- page 24 ---
18 
 
Presentation Layer 
The presentation layer is concerned about displaying and letting the user interact with 
the data. This layer uses the MVVM design pattern which stands for Model-View-
Viewmodel, and is the recommended way of writing applications in Xamarin.Forms. 
2.2.3 Layer Relations 
Presentation Layer to Business Logic Layer 
The presentation layer represents the user interface of the application whereas the 
business logic layer (BL) contains the services and controllers which implement the 
actual logic what happens when the user interacts with the application. As we use 
MVVM, the viewmodels calls the services and controllers from the BL. 
Business Logic Layer to Data Access Layer 
The business logic la yer communicates with the data access layer to get the data that 
we need from the local storage.

Figure 2.5. Layer interaction for OrderAppointment View 
In the above figure we can see how the layers interact with each other using the 
example of the OrderAppointment view. The view binds the list of appointments to 
the OrderAppointments property in the viewmodel. The viewmodel populates this list 
by requesti ng the relevant appointments from the service. The service on the other 
hand implements the logic to query for the correct appointments and uses the 
DbContext, which is implemented in our data access layer (Entity Framework) to 
execute the query. The DbCon text sends a SQL query to the database and returns our 
appointments that we requested. The appointments will go through every layer until 
they reach the viewmodel and update the list property. The viewmodel then notifies 
the view that the list property has changed and the view will update. 
Each of the layers have their own responsibilit ies such that the viewmodel is only 
responsible for keeping the state of the view and calling the correct service methods 
when the user interacts with the view. 
2.2.4 Design and architectural patterns  
A software design pattern is a reusable  solution to a frequently occurring problem in 
software engineering. It is not a finalized design that can be turned into source code or 
machine code right away. Design patterns are well -defined best practices that 
programmers may employ to overcome common issues.[3] 
Visitor Pattern 
The problem that was faced during the development of the application was that we 
have 13 different controls and each of the control works quite differently for example 
a group control does not have a result value, whereas all the other controls do. But 
also, all controls have different types for their return  types. And as all checklists are 
dynamically created, we have no way of knowing before runtime what type of control 
we are dealing with. A simple approach would have been to just create an interface 
which is implemented by all controls and defines a metho d to get the result, but as the 
controls have different return types for their value this was not as simple as that. 
Instead, we implemented the visitor pattern, which makes it possible to define a new 
operation for some classes of an object structure with out changing the classes itself. 
For that we have to define a visitor object which implements the operation to be 
performed on elements of an object structure. 
MVVM 
The presentation layer is implemented by using the Model -View-ViewModel 
structural design pattern, which separates objects into three categories: 
A model holds the actual application data, such as the domain model. The view 
displays the visual elements and controls on the screen. Lastly, the ViewModel 
represents the state of the view.

Figure 2.6. Model-View-ViewModel pattern [4] 
The figure above shows how the three elements are working together. The view has 
bindings to properties and commands in the view model. The view model does not 
know about the view and is therefore decoupled. When a property changes in the view 
model, INotifyPropertyChanged is raised and a notification is sent to the view that the 
property has been changed and needs to be updated. On the other hand, the view 
model is responsible to update the model to make changes to the model, the actual 
data itself. For example, when we have the appointment details page, where we can 
manipulate an appointment, we are actual only changing the data of the view model 
but when we click save, the view model is responsible to call the proper business 
logic to update the model and then persist the changes. 
Dependency Injection 
Dependency injection is a variant of the inversion of control approach. A client should 
not have to know how to create certain services in order to use them. Instead, the 
client defers to third -party code (th e injector). The injector is unknown to the client. 
The injector provides services to the client, which may already exist or be created by 
the injector. Then after, the client makes use of the services.  In detail that means, our 
viewmodels which are the ma in consumer of these services do not need to know how 
to create its dependent services, but rather the service is injected and resolved via an 
Inversion-Of-Control (IOC) container. This is especially critical for writing tests, 
writing any kind of tests fo r classes and methods which are using these services is 
hard to handle. For example, if the service communicates with the internet, but during 
the test there is no internet the test would fail but the actual implementation is actually 
correct. Instead, we can inject fake-services which will be resolved when tests are 
running. These fake -services are easier to control such that the output data is always 
the same.

4.3 Code quality 
This section is about how to keep the code clean, maintainable and extensible. 
Creating a simple mobile application with a few defined features at the beginning is 
not a complex task, but creating an application which can add new features at will in a 
feasible time for the implementation and also is understandable by developers who 
never worked on the project before is a challenge. Luckily there are already people 
much smarter than me who have found solutions to these  problems. Two guidelines 
which I have followed when implementing the mobile application are Clean Code 
and SOLID principles. 
SOLID principles 
SOLID is an acronym for software design principles to make code more 
understandable, flexible and maintainable. B ecause what happens often is that after 
finishing the initial product unforeseen feature and change requests are difficult to 
implement as everything is very tightly coupled and changes are breaking existing 

--- page 39 ---
33 
 
behaviour. In this section I will explain each principle but only focus on the first and 
last principle, further I assume that the reader is somewhat familiar with these 
principles. 
Single-responsibility principle 
Probably one of the easier principles to understand and implement is the single 
responsibility principle, which means that every class should have only one single 
responsibility. In practice that means we do not want to have classes which have 
many different use cases but are only being used for one single thing. For example, in 
our business logic layer we have our services for each type of domain model, these 
services all have one thing in common they all are only responsible for the business 
logic of a single domain model. More precisely they implement the CRUD logic of its 
corresponding domain model. 
Dependency inversion principle 
The dependency inversion principle is based on the Open/Closed and Liskov 
Substitution principle. We introduce interfaces in o rder to make components open for 
extension but closed for modification . Secondly, implementations of these interfaces 
can be replaced at will, without breaking the application. With those principles 
implemented we can focus on the dependency inversion principle which allows us to 
use a very powerful tool in modern day programming: Dependency Injection 
Dependency inversion means that high level components should not depend on low 
level components but rather depend on abstractions (interfaces). If this is not  given, 
our application is tightly coupled and any changes being made in the future can cause 
problems.
