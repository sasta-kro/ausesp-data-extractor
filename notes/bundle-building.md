# Building the content bundle

`pipeline/build_import_bundle.py` assembles everything the AUSE Discovery
content import needs into one portable bundle inside the main repository
(`resources/REAL_IMPORT_BUNDLE/`):

```text
project-content-manifest.json
logos/<identifier>.png
projects/sp-<identifier>/<file>
```

Inputs: the metadata CSV (membership), `output/extraction-evidence/manifest.json`
(logos and repository links), `output/logos/`, and
`_workspace/extracted-sources/`. Paths live in the configuration block at
the top of the script, so a repository move is a one-line edit. The bundle
is rebuilt from scratch on every run and is never the only copy of
anything. `--dry-run` validates and prints the plan without writing.

The manifest contract is enforced by the application loader (strict JSON,
unknown fields rejected), so the script validates everything locally the
same way: exact key sets, exactly one primary link per project, RFC 3339
liveness timestamps, HTTPS URLs, PNG logos within 2 MiB and 1600 px,
files within 250 MiB, and detected-content checks against each file's
extension.

## Membership

Only projects present in the metadata CSV enter the bundle. This is the
single filter, with no hardcoded project exclusions, so culled duplicates
and the five unimportable projects can never reference a Project that has
no database row. Current result: 209 members produce 209 manifest entries.

## File classification

| Corpus file | Artifact type | Display name |
|---|---|---|
| `report.pdf`, `report.docx` | `report` | Final report |
| `slides.pdf` | `slides` | Presentation slides |
| `poster.pdf`, `poster.png`, `poster.jpg`, `poster.jpeg` | `poster` | Project poster |

`media/` and `doc-convert/` directories are extraction byproducts and are
never bundle content. `external/` directories hold supplementary material
submitted beside the report (published conference papers, a confirmation
letter, a feedback report). Files there import under the `other` type when
their extension is permitted, which covers the six PDFs. The three YRSS
2021 award images in sp-2039 (jpg, png) have no type that permits their
extension, so they stay out and the build reports a warning for each.

## The sp-26027 external report

The `external/` copy of the MCG Care 2.0 report was compared against the
staged core report (2026-09-12, full text diff). It was a redundant
near-duplicate: identical students, advisor, approval page, abstract,
table of contents, figures, and references, with everything from chapter
3 onward byte-identical. Its only unique content was a "Team 2Byte1Bit"
line on the cover, and its embedded creation date was one day older. The
file was deleted from staging (2026-09-12) and the staged core report is
the one imported.

## Repository links

Only `kind == "project_repo"` evidence becomes a manifest link, so
third-party references never reach the application. Liveness maps to the
application availability enum: `public` to `accessible`, `not_found` to
`not_accessible`, anything else to `unverified`. The `links` field is
omitted entirely for projects without repository links, because an
explicit empty array would instruct the application to remove links.

## Legacy format conversions

The application extension table admits no `.doc` file anywhere and no
`.pptx` under the `poster` type. Three corpus files are therefore
converted to PDF before bundling (LibreOffice, headless, cached under
`_workspace/converted/` so rebuilds do not reconvert):

- `sp-1636/report.doc` -> `report.pdf` (68 pages). The project's only
  file, so without the conversion it had no bundle entry at all.
- `sp-1638/poster.pptx` -> `slides.pdf` (10 slides). The corpus named it
  a poster, but it is a presentation deck (16:9 slide geometry).
- `sp-1703/poster.pptx` -> `slides.pdf` (16 slides). Same situation.

A staged file already carrying the converted target name always wins over
a conversion, so the rules stay safe if a project ever gains a real
`slides.pdf` beside a legacy deck.

## Superseded manual path

Before this script existed, the manifest was generated by the two `jq`
commands recorded in the main repository operator note
(`.memory/sasta-dev-notes/project-content-import.md`) plus a manual copy
of `output/logos/`. Those commands remain valid for one-off logo-only or
links-only exports. The script is the primary path because it also carries
the project files, which `jq` never did.
